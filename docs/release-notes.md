# Release notes

Every merged change adds a line under **Unreleased** in the right section.

## [Unreleased]

### Changed

- School leads list and detail show the assignee's name from `assigned_name`. The staff id in `assigned_to` is still used when saving who is assigned; it is not shown in the list.
- Landing **School sign in** goes to `/school` (the school staff portal), not `/admin`.
- View as this student on an account matches its board. Staff confirm with a required reason (drawn, not sent — the impersonate call has no body), then a sticky banner shows while the session runs. End session calls `POST /api/v1/users/{user_id}/impersonate/end` with the staff token. The view token stays in memory only and never replaces the staff token; the student surface is not mounted in the admin console yet.

### Added

- School and admin sign-in on the web include Forgot password: request a reset code, enter it, set a new password, then sign in again. Same APIs as mobile (`POST /api/v1/auth/codes` with `purpose: "reset"`, then `POST /api/v1/auth/password/reset`).
- Web deploy path: Docker image (Next.js standalone) pushed to GHCR and pulled onto a VPS with `docker compose`. On the shared DEV host the app is published on port **3004**. Push to `dev` runs the DEV workflow; `main` is the PROD copy. Secrets and first-time VPS steps are in [Deploy the web app](how-to/deploy-web.md).
- Mobile enrolment manage (M-Enrolment): Me → Your class shows the current enrolment, subjects and school year. While `window_open` and changes remain, Change it now opens the class picker (corrections). After the window closes, Ask for a change posts a staff change request. Past request history stays marked as API to be added (no student list endpoint).
- Mobile enrol flow matches M-Enrol-Optionals / Confirm: after class (and stream) the app opens optional subjects from the catalog pool, or “Decide later”, then a confirm screen (optional parent phone via `parent_contact`) before `confirm`. Corrections for an already-confirmed class still use the corrections endpoint.
- Mobile Alerts tab lists `GET /api/v1/notifications` (titles and bodies from the server), with mark-one and mark-all-read. Guardian flow: students invite a parent with relationship (`POST /me/guardian-invitations`) and can resend; parents list and accept or decline pending invites. Parent-started ask-to-link and student name on the accept card stay marked as API to be added.
- Mobile parent home matches M-Parent-Home / Add-Child / Child-Detail. Parents see their children from `GET /api/v1/me/children`, can add a child (`POST /api/v1/me/children`), and open a child to edit the name, sign devices out, set a password, or close the account. Learn and Search tabs are hidden for parents. Class and stream on the list, and a parent-started “ask to link”, stay marked as API to be added.
- School staff portal at `/school` matches the School-* boards for Overview, People and School details. Membership comes from `GET /api/v1/me/schools`. People uses organisation members (add/remove). Details uses organisation GET/PATCH. Students, Add students and Progress are stubs with "API to be added". Seats, counts and progress on Overview are drawn as "—" and marked the same way.
- Possible duplicates at `/admin/duplicates` matches its board. Open pairs come from `GET /api/v1/users/duplicates` with cursor pages. Same person and Different people call the decision endpoint. Account name, date of birth, sign-in and created come from each user; enrolment and last active are marked "API to be added".
- Change requests at `/admin/change-requests` matches its board. Waiting, approved and refused requests come from `GET /api/v1/enrollment/change-requests`, with a status filter and numbered pages. Approve and Refuse call the decision endpoint with an optional note. Student and decider names are looked up; the Now column, pool check and what she loses are marked "API to be added".
- Releases at `/admin/releases` matches its board. Releases for the chosen subject come from `GET /api/v1/content/releases`. Start opens a new version, Publish asks first then publishes, and Pin this sets a course for the current year onto that release. Open and Pinned are worked out in the console. Counts on the open release, who started it, and pinning when no current-year course exists are marked "API to be added".
- Edits at `/admin/content/changes` matches its board. Waiting, approved, rejected and applied-at-once changes come from `GET /api/v1/content/changes`, with status and kind filters and numbered pages. Approve and Reject call the decision endpoint; a reject note is optional free text. The Now column, author and subject names as fields on the change, and See it are marked "API to be added".
- Add a question at `/admin/content/new` matches its board. A chapter, topic and idea are created first, because those levels cannot be listed, and that is marked "API to be added". Saving creates the question, then submits and approves the review the server opens. Checked by, the reference and free labels are drawn and not sent. The question is saved against a school on the signed-in account.
- The Content page matches its board. Courses for the chosen academic year come from `GET /api/v1/content/courses`, with numbered pages because that list returns a total. Subject and grade names are looked up and marked "API to be added" as fields on the course. The version link and Change version go to Releases. Pending edits shows how many changes are waiting. Add content and the edits page are linked and still being built.
- Subjects and subject pools match their boards. Subjects come from `GET /api/v1/curriculum/subjects`, filtered by grade and stream, with Rows and a count of the page. Add a subject asks first, then creates it; the name and code cannot be changed afterwards. Readiness is saved with the availability endpoint. In the pool is read from the published pool for that grade and stream. A pool draft can add, remove and switch subjects, change how many must be picked, and publish after a confirmation that names what changed. Draft, Live and the version counts are worked out in the console and marked "API to be added".
- The Curriculum page matches its board. Academic years come from `GET /api/v1/curriculum/academic-years`. Add a year and Edit dates save the label and the two dates. Make current asks first, then calls the current-year endpoint and takes effect at once. Current is the field the API returns. Next and Past are worked out from the dates and marked "API to be added" as fields. Grade levels and streams are read-only lists. Subjects and subject pools are linked from this page.
- Roles, a role, and a person's access match their boards. The roles list is every role from `GET /api/v1/rbac/roles`, split into platform and organisation, with no further pages. Saving a role replaces its description and its whole permission set. A custom role can be deleted; a built-in role cannot. Access on an account gives and takes away roles and direct permissions, and shows what is in force. Permission names are whatever the permissions list returns. The People count, who holds a role, and a note or expiry on a direct grant are marked "API to be added". A paused or closing account shows that state on the account page. Resume and stop-the-closure call the account API, and the days left come from the purge date. Who paused the account, and who asked to close it, are marked "API to be added".
- Web admin at `/admin` for the admin API: school leads, platform settings, notification webhooks, the delivery log, and publishing site pages. Sign-in uses the cookie session.
- Schools on the web: a public enquiry at `/schools`, and staff can create a school, change its status, and add or remove a person. Creating a school does not create its staff login.
- The public home page follows the design boards: cream hero, how it works, subjects, parents, pricing, and a school band. Invented counts and the sample quote are left out. The school enquiry at `/schools` still posts to `POST /api/v1/public/school-leads`.
- Staff sign-in and the admin console use the board layout (sidebar, overview). The overview reads live school leads, organisations and `GET /api/v1/me/schools`. Accounts, curriculum, content and the school student screens stay out because those boards have no matching API yet. Set `NEXT_PUBLIC_API_BASE_URL` to `https://api-koeshaa.thebitrates.com` to use the hosted API.
- The admin console matches the admin boards exactly: its own colour group in `@keoshaa/tokens` (`admin.*`), 14px text, a sidebar that folds to an icon rail (remembered on this browser), a page header with the English/Nepali switch, and table pages with Rows and Previous/Next. Overview and School leads are done. Parts with no API yet (seats, contracts, lead search and sorting) are drawn as designed and marked "API to be added". In Nepali, dates use the Bikram Sambat calendar (`nepali-date-converter`, about 3 KB gzipped, admin only). Accounts, Roles, Curriculum, Content, Releases and Change requests have routes that say the page is being built next.
- The school lead page matches its board: enquiry, what happens next, handling and change history. "Mark contacted" and "Create the school" work. Creating the school calls `POST /api/v1/organisations` with the lead's name and phone, then links it to the lead and marks it won; if linking fails, a retry reuses the school instead of creating a second one. "Assigned to" lists staff by name from `GET /api/v1/users?account_kind=staff`. The full change history is marked "API to be added" because there is no lead history endpoint.
- The Schools page matches its board: "Your schools" cards from `GET /api/v1/me/schools`, and "All organisations" with name search, kind filter and Rows with Previous/Next on `GET /api/v1/organisations`. "Create a school" in the header opens the create form as a panel and links to the new school once it is made. Seat counts and sorting are drawn but marked "API to be added".
- A school page matches its board: profile (saved with `PATCH /api/v1/organisations/{id}`), people from the members API, and change status. "Add a person" finds the account by phone, email or username (`GET /api/v1/users`) and adds them; removing someone ends only their membership. Contract, seats and student counts are drawn and marked "API to be added". Province and district are typed, because the API stores them as text.
- The Settings list matches its board: one paragraph, a search box and a scope filter, then every setting from `GET /api/v1/admin/settings` with no pages. Search and sorting happen in the browser. Grade level is listed but marked "API to be added", because every setting the API returns is platform-wide.
- A setting page matches its board: what it does, the value with its allowed range, the default and the scope, plus the change history from `GET /api/v1/admin/settings/{key}/history`. Save and Reset to default both use `PUT`. A person who changed it is shown by name; a change with no account says System. "What this touches" is marked "API to be added".
- Text links in the admin console are underlined, matching the boards. The sidebar, the back control, cards and buttons stay without a line.
- An account page matches its board. It loads the person, sign-in methods, guardian links and consents. Save edits the name, language and date of birth. Add and Remove change sign-in methods, and the last method cannot be removed. End link removes a guardian. Record a consent posts the document and version. Pause, resume, close, stop the close, sign out of every device, and a staff authenticator reset call the account API. View as this student starts a read-only session and discards the token; the student screen is still being built. Class and school are "—" because they are not fields on the account. Roles stay on the access screen, which is still being built.
- The Site pages screen matches its board. Terms, Privacy and About load from `GET /api/v1/site-pages/{slug}` for the chosen page language, and Publish posts a new version. A language with no published text stays empty, even when the API falls back to English. Save draft and the header Preview are marked "API to be added". The published time is shown; the API does not say who published it. The body is a Markdown editor: formatting buttons, Ctrl or Command with B, I and K, and a Write / Preview switch that renders the text on the page.
- The Accounts page matches its board. Search uses `GET /api/v1/users`: exact on a phone, email, username or Google id, and a name prefix, with an account-kind filter and Rows with Previous/Next. Names open the account page, which is still being built. "Create an account" opens a panel and posts the name, kind and one sign-in identifier. The Duplicates link shows how many open duplicates the first page returns. Capacity is "—" because it is not a field on the account.
- The Deliveries page matches its board. The log comes from `GET /api/v1/notifications/admin/deliveries`, with status and channel filters and Rows with Previous/Next. Kind, channel, status, tries and when sort the rows on the current page. Addresses are shown as the API returns them, already masked, and the time is the Kathmandu clock time of the last update. The four counts and Export CSV are drawn and marked "API to be added".
- The Webhooks page matches its board. The list comes from `GET /api/v1/notifications/admin/webhooks` and shows the name, the host of the URL, the format, the events, and Active or Paused. Sorting applies to the rows loaded so far; further rows use Load more. The state pill pauses or turns an endpoint back on, and Remove deletes it. Add webhook stays on the page. The signing secret is shown once, with Copy, and is not shown again after "I have stored the secret".
- Real students see the free chapter names for their class. Opening one still says lessons are coming soon, because the API has no lesson body yet.

### Security

### Fixed

- Web Docker image build installs `@tailwindcss/oxide-linux-x64-gnu` so Next.js can compile CSS on Linux CI (the Mac lockfile only pulled in the darwin binding).
- Mobile tests that load the student's class mock `GET /api/v1/catalog/academic-years/current` and a full enrollment payload again, so Learn/Home no longer fail as a generic server error in CI.
- School portal routes opt out of Next.js Instant Navigation validation (`instant = false`), matching admin. Signed-out `/school` no longer reports a dropped `page.tsx` segment in the Instant overlay.
- Staff authenticator setup shows a QR code from the server's authenticator link, with the key beside it. Recovery codes stay on screen until they are saved.
- The sign-in screen fills the window. The cream page background no longer shows as a strip under the teal and mist panels.
- The public home hero matches the landing board: a two-line promise, the phone question with its streak, and the soft colour behind the headline. Invented student, school and province counts stay off the page.
- The school enquiry page matches the Talk to us board: a message box, the receipt under After sending, and a light footer. Terms and Privacy stay off until those pages exist.
- The admin overview matches the home board: school, open-lead and failed-delivery counts from the API, a waiting time on each lead, and a failed-delivery notice. Seat totals and contract warnings stay off because the API has neither.
- Reloading admin shows the shape of the page while the session and lists load, instead of a plain Loading line.
- Switching between admin pages keeps the sidebar. The full-page skeleton only shows while the session is being restored.
- The sign-in password box has one border. Typing a username no longer repeats “Username” under the field.
- Opening admin with no connection shows the sign-in page. A failed session check no longer replaces the page with a connection error.
- An empty Leads to call list uses the same inset as a lead row. It no longer adds a second heading inside the card.
- Admin lists use the board table: school leads, schools, settings, webhooks and deliveries. Each column has the same padding as a lead row, and status sits in a pill.
- The school-lead and delivery filters stay a short control. They no longer stretch across the page.
- The admin shell keeps a left sidebar from tablet width up. On a phone the sections open from a menu instead of wrapping across the top.
- Filter menus use a designed list, and the arrow sits inset from the right edge.
- Public footer links sit on their own rows. Talk to us, School sign in and Pricing for schools no longer run together.
- The mobile TypeScript config points at Expo's base file directly, so the editor can load it from this workspace.
- Sign-in, sign-up, password reset and recovery send phone numbers and emails in the backend's normalised form. A code screen shows the masked destination the API returns.

### Changed

- The admin sidebar stays fixed while the page scrolls. Sign out is in the account options menu at the bottom of the sidebar.
- Design token names are now semantic (`primary`, `onPrimary`, `reward`, ...) with `light` and `dark` sets; the web `@theme` is generated, and the web placeholder uses `text-primary`.
- Minimum touch target raised from 44 to 48 (`minTouchTarget` in `@keoshaa/tokens`).
- Frontend standards updated: styling (NativeWind 4 on mobile, Tailwind v4 on web, both generated; arbitrary Tailwind values now fail lint), the `components/ui` list is the minimum set, and "Current state" reflects what is built.
- Token drift tests now live with each generated file's owner (web and mobile apps); `tokens:generate` sits next to `api:generate`.
